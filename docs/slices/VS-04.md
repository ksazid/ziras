# VS-04 — Malta Production Source Adapter Pack

## Goal

Convert the broad OSS/vendor qualification work into a governed first-party Ziras source-pack layer without building one scraper per vendor and without enabling unreviewed production collection.

## Approved scope

1. Add a declarative `SourceProfile` registry for the first Malta source set.
2. Reuse the certified deterministic structured-data extractor instead of duplicating vendor parsers.
3. Enforce source policy before normalization; unknown/unapproved sources fail closed.
4. Enforce HTTPS and per-profile domain allowlists before source content is accepted.
5. Separate policy state from technical capability: `review_required`, `partner_required`, `approved`, `prohibited`.
6. Keep Scrapy static-first acquisition and Playwright fallback behind ADR-001 acquisition boundaries; VS-04 does not let the HTML adapter fetch arbitrary URLs.
7. Add deterministic tests for policy denial, explicit partner-policy approval, partner execution context, domain boundaries, shared retail/event/deal extraction and deduplication.
8. Track live Malta inventory evidence separately from permission to collect it.

## Why declarative profiles

The same core operations recur across vendors:

- source-policy decision;
- robots requirement;
- domain/HTTPS boundary;
- static HTML acquisition;
- optional browser fallback;
- schema.org/structured metadata extraction;
- deterministic price/date normalization;
- source observation + provenance;
- discovery normalization;
- entity resolution/freshness/ranking downstream.

These should remain shared engine capabilities. Vendor-specific code is introduced only when a source genuinely cannot be represented by the shared contract.

## Live inventory evidence at slice start

Observed on 2026-08-31 during source review:

- VisitMalta exposes a public events catalogue with dated event listings and a sitemap generated for machine discovery/search indexing.
- Deal.com.mt exposes substantial active Malta deal inventory across food, activities, hotels and retail categories and advertises a partner path.
- SCAN and Greens expose current ecommerce/product inventory publicly.

These observations prove source usefulness only. They are **not** source-policy approval.

## Acceptance criteria

- Every source profile has a stable key, domain allowlist, source kind, entry URL(s), policy stage and robots requirement.
- Candidate registry automatically denies every review-required source.
- Candidate registry also denies every partner-required source until a reviewed `PARTNER_ONLY` SourcePolicy is registered.
- An approved partner-only policy still requires explicit partner execution context.
- Unknown source keys fail closed.
- A source URL outside the configured HTTPS domain set is rejected even if a policy record exists.
- VisitMalta fixture normalizes to an `EVENT` only after explicit test policy approval.
- Deal fixture normalizes to a `DEAL` only after explicit partner-policy approval and in partner context.
- Retail fixture uses the shared structured extractor and preserves deterministic price/date parsing.
- Duplicate normalized structured items are removed within one page result.
- No production source scheduler, credential, proxy, CAPTCHA bypass, anti-bot bypass or robots override is introduced.
- Existing Meta, kernel, PostgreSQL/PostGIS/pgvector and PES gates remain green.

## Explicitly out of scope

- approving any source's production scraping policy;
- scraping Bolt/Wolt or Meta HTML;
- proxy rotation / stealth / anti-bot bypass;
- continuous production crawling;
- merchant onboarding;
- source-specific brittle CSS parsing when shared structured extraction is sufficient;
- treating a visible public page as automatic permission for automated collection.
