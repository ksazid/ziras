# VS-06 — POC Coverage & Extraction Hardening

Status: Implementing

## Objective

Close the validation gaps recorded by the first VS-05 Malta POC report before any user-facing feed work.

## Approved scope

1. Split Eden route semantics: `/special-offers` uses promotion extraction and `/whats-on` uses event extraction.
2. Harden browser-source validation so VisitMalta cannot report a healthy run when a rendered page yields no event candidates.
3. Add deterministic browser-rendered event fixture coverage for the VisitMalta acquisition path.
4. Qualify two additional Malta-local source classes using current public policy evidence and strict source controls.
5. Preserve existing ingestion, freshness, dedupe, provenance and ranking invariants.
6. Prepare the source set for a formal `poc` ingestion metrics run.

## Existing POC-source hardening

### Eden Cinemas

- `/special-offers` → `promotion`
- `/whats-on` → `event`
- route semantics are data-driven via longest matching path prefix.
- no Eden-specific conditional is added to the pipeline.

### VisitMalta Events

- remains browser acquisition.
- `minimum_candidates = 1`.
- a successful HTTP/browser render that yields zero normalized events is recorded as `insufficient_candidates` rather than a healthy source result.
- observation/evidence is retained for diagnosis, but an unhealthy zero-candidate result does not populate the ranked feed.

## Hardening configuration boundary

VS-06 introduces `malta-source-hardening.json` for extraction-only metadata:

- `route_adapter_kinds`
- `minimum_candidates`

The certified `malta-source-policy.json` remains authoritative for source access mode, policy scope, allowed paths, request caps, attribution and storage rules. The hardening loader rejects attempts to override any policy/catalog-authority field.

## Additional-source qualification

The PRD requires at least five independent POC source types; the currently approved set has three.

Two additional candidates are being qualified, but **no candidate is POC-approved by the VS-06 scope/implementation approval itself**. Each candidate requires an explicit source-policy approval before its access mode/scope can be changed or POC acquisition can run.

Qualification criteria:

- API/open-data/license or explicit permitted-access basis;
- robots/technical controls where applicable;
- commercial/POC reuse conditions;
- attribution and caching/retention obligations;
- Malta-local discovery usefulness;
- acquisition reliability and expected discovery density.

Research-only sources such as Lidl/Eurospin must not be upgraded merely to satisfy the source-count metric. Sources with restrictive terms remain denied/partner-only.

## Out of scope

- implicit approval of newly qualified sources
- production source enablement
- scheduler activation
- release approval
- anti-bot, stealth, proxy rotation or CAPTCHA bypass
- merchant onboarding
- user-facing feed/UI

## Acceptance criteria

VS-06 can reach certification readiness when:

- route-aware semantics and source-health checks pass deterministic tests;
- all prior discovery-engine regression tests pass;
- PostgreSQL integration passes;
- PES preflight passes;
- additional-source qualification evidence is recorded truthfully;
- no new source is promoted without explicit policy approval;
- no prohibited source is accessed beyond its approved scope.

VS-06 certification alone does **not** pass the product POC. Formal ingestion metrics and the PRD 14-day thresholds remain separate validation evidence.
